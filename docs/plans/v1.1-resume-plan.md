# DuoHive v1.1 Implementation Plan — Resume an old session

**Status:** Plan, drafted 2026-10-31 · not started · starts after v1 is released (v1 roadmap phase 5). Awaiting the author's review.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `r` on a stopped or errored agent opens a picker of the Claude Code or OpenCode sessions in the agent's directory and kept worktrees, and the agent continues the chosen session at rest, with its full context.

**Architecture:** The core owns the types and a `SessionCatalog` port (no I/O). `duohive-cli` implements it by reading Claude Code's session files and running `opencode session list`; the binary calls it off the core task, as it does for model lists, and answers with an `Input`. The engine marks sessions in use from a new `sessions.cli_session_id` column, and resumes through the existing launch path with a `resume` field on `LaunchSpec`. The picker is a new TUI dialog.

**Tech stack:** Rust 1.99.0, edition 2024; Ratatui and crossterm (pinned with `=`); rusqlite; tokio `spawn_blocking`; `serde_json`.

**Specs (the plan argues from these; read them first):** [PRD *Resume an old session (v1.1)*](../product/prd.md) · [UI §4.13](../ux/ui-spec.md) · [TD §5.6](../design/technical-design.md#56-resume-an-old-session-v11-planned) · [v1.1 roadmap](v1.1-roadmap.md). No behaviour changes in this plan; a spike that contradicts a spec stops the task and goes to the author (V11-D2).

## Global Constraints

Every task includes these (from [AGENTS.md](../../AGENTS.md) and Phase 0's [Global Constraints](phase-0-plan.md#global-constraints)):

- Toolchain 1.99.0, edition 2024, licence Apache-2.0. `make check` (format, clippy, tests, `cargo deny`, `typos`) passes before every commit. Conventional commits; never a `Co-Authored-By` line; never push.
- No `unwrap`/`expect` outside tests; no `unsafe`.
- `duohive-core` does no I/O and depends on no `duohive-*` crate; the other crates depend only on `duohive-core`; only `duohive` depends on all.
- Never modify the user's global CLI configuration: reading `~/.claude/projects/` and running `opencode session list` are read-only.
- No `std::env::set_var` in tests; tmux tests use a throwaway socket, never `duohive`.
- Supported CLIs: Claude Code and OpenCode only.
- Test first, except for the spikes (V11-D1).
- A session id reaches a command only as one argument in `LaunchCommand.args` (passed verbatim), never inside a shell string.

## Review Focus

The specs are silent on these; each has a test in the owning task, most likely first.

1. A session file that is huge, truncated, empty or not JSON, or a title with control characters or ANSI escapes: the entry is skipped or sanitised, the picker never crashes or garbles the screen (R.9, `claude_catalog_skips_unreadable_files`, `title_strips_control_characters`).
2. A session directory spelled differently from the agent's (trailing slash, `~`, a symlink): it still matches (R.9, `directory_match_resolves_symlinks_and_slashes`).
3. Two agents resume the same session in the same moment, before either hook has recorded an id: the second is refused (R.8, `second_resume_of_same_session_is_refused`; the id is recorded at launch, not only from the hook).
4. A session id that is not a plain id (spaces, quotes, `;`): refused before launch (R.8, `resume_rejects_odd_session_id`).
5. Thousands of sessions in one directory: listing stays off the core task and the picker stays responsive (R.9, `claude_catalog_reads_metadata_only`; open question V11-Q2 on a cap).

| # | Decision |

| V11-D1 | **Spikes first, no tests.** R.1 to R.3 are throwaway spikes like S1 to S4 (TD §5.2); their results go in [spike-report.md](spike-report.md). Every task after them is test first. |
| V11-D2 | **A spike never changes behaviour on its own.** Where a result contradicts the PRD or UI, the task marked *Fallback* says what to do for the code; if the fallback changes what the user sees, the task stops and the author decides before the docs change. |
| V11-D3 | **Listing is a port, answered by an `Input`** (the model-list pattern in `duohive/src/system/models.rs`): the engine asks, the binary reads on `spawn_blocking`, the answer arrives as `Input::SessionsListed`. The core task never blocks. (My call, as the closest existing pattern.) |
| V11-D4 | **The session id is recorded twice:** at launch (the id we resumed) and from the first hook (a fresh session's id). The first closes the same-moment race; the second covers sessions DuoHive did not choose. (My call, from Review Focus 3.) |

### Task R.1: Spike R1 — Claude Code `--resume`

**Files:** `docs/plans/spike-report.md` (new section *R1*). No product code.

- [ ] **Step 1: Run the checks** against the pinned Claude Code version, in a throwaway directory with a throwaway session, and record the command and result for each:
  - `claude --resume <id>` together with `--settings <file>`, `--append-system-prompt`, `--mcp-config` and `--model`: starts, shows the old conversation, takes the per-launch hooks.
  - The `SessionStart` payload: does it carry `session_id`, and is it the original id after a resume (or a new one)?
  - The session files under `~/.claude/projects/<folder>/`: how a directory maps to `<folder>`; which fields give the title, last-written time (file mtime), git branch and size; how a session with no title shows its first prompt.
  - A worktree directory: where its sessions are stored.
- [ ] **Step 2: Write the findings and the exact reader rules** (file glob, JSON fields, folder-name encoding) in `spike-report.md`, with the CLI version.
- [ ] **Step 3: Commit.** `docs: spike R1, claude code resume`

**Fallbacks (record the one that applies):**
- *`--resume` refuses one of the per-launch flags:* R.9 omits that flag on resume and the task stops for the author (the role instructions or hooks would be lost).
- *The hook `session_id` is absent or changes after a resume:* R.6 records the id we launched with (V11-D4) and, for a fresh session, the newest session file's id in the directory after `SessionStart`.
- *The title, branch or size is not in the file:* the picker shows what exists; a missing field is left out of the line (UI §4.13 already cuts a missing title to the first prompt).
